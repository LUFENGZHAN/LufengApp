# LufengApp 三层架构改造方案（前端 + 后端 + 数据库）

> 目标：把当前「Spring Boot 单体骨架 + Android 空模板」改造为 **前端 / 后端 / 数据库各自独立成模块** 的带用户认证在线聊天系统，Web（Vue 3 + Vite）与 App（Android 原生 Java + XML）**复用同一套 REST + WebSocket 接口**。

---

## 0. 现有代码分析

### 0.1 现状盘点

| 模块 | 现状 | 评价 |
|---|---|---|
| `backend/` | Spring Boot（Gradle，Java 21）+ MyBatis 3.0.4 + MySQL + Redis + WebSocket + Validation | 技术选型基本正确，但只有认证骨架 |
| `backend/.../app/user/` | `AuthController`（login/register/user）、`AuthServiceImpl` **全部 TODO**，`login()` 直接返回硬编码 `test-token` | 业务逻辑空，仅接口形态可用 |
| `backend/.../common/` | `Result`、`@LoginRequired` + `LoginInterceptor`、`@RequestDTO` + `RequestDTOResolver`、`GlobalExceptionHandler`、`WebConfig` | 有统一返回值意识，是本次改造的主要可复用资产 |
| `backend/src/main/resources/sql/` | `user_account.sql`、`user_profile.sql`、`user_session.sql` | 三张表设计合理，缺会话/消息/好友表 |
| `backend/src/main/resources/static/images/default-avatar.png` | 默认头像 | 可直接复用 |
| `android-app/` | Android Studio "Empty Views Activity" 模板，`com.example.applicatio`，`FirstFragment`/`SecondFragment`/lorem ipsum | 纯脚手架，业务代码 0 |
| 前端 | **不存在** | 需新建 `web-frontend/` |
| 数据库 | 无 docker-compose、无统一初始化脚本 | 需新建 `database/` |

### 0.2 可直接复用（改造后保留）

1. **`Result<T>` 统一响应包装器** → 升级为带 `code/message/data/requestId/timestamp` 的版本，并配套 `ResultCode` 枚举。
2. **`@LoginRequired` 注解 + 拦截器思路** → 升级为真正校验 JWT 签名的 `AuthenticationInterceptor`，并把用户上下文写入 `AuthContext`（ThreadLocal），校验失败抛 `BizException(401)` 交给 `GlobalExceptionHandler` 统一输出。
3. **`GlobalExceptionHandler`** → 扩展处理 `BizException / MethodArgumentNotValidException / ConstraintViolationException / NoResourceException`，禁止把堆栈信息返回给客户端。
4. **实体 `UserAccount` / `UserProfile`** → 账户与资料分离的设计是对的，保留并扩充字段（`token_version`、`password_algo`、`deleted_at` 等）。
5. **`user_session` 表思路** → 升级为 `user_device_session`（`device_id` + `refresh_token_hash` + `access_jti`），支撑多端在线与刷新令牌轮换；原表 `uk_user_device` 唯一键思路保留。
6. **MyBatis + MySQL** 持久层组合 → 保留，历史消息拉取写 XML Mapper 便于做游标分页 SQL 优化。
7. **已引入的 Redis / WebSocket Starter** → 正好是本次长连接与在线状态所需，无需新增依赖。
8. **Android 工程的 Gradle 结构**（`libs.versions.toml` 版本目录、ViewBinding、`nav_graph`）→ 保留，仅替换页面与新增依赖。

### 0.3 必须改造 / 废弃

| 项 | 问题 | 处理方式 |
|---|---|---|
| `LoginInterceptor` | 只判断 `Authorization` 头**是否为空**，不做任何签名校验，等于无鉴权 | 删除，改写为 JWT 校验拦截器 |
| `AuthServiceImpl.login()` | 返回硬编码 `test-token` | 重写为 JWT 签发流程 |
| `@RequestDTO` + `RequestDTOResolver` | 重复实现 Spring 已有的 `@RequestBody`/`@ModelAttribute`，且手工调用 `binder.validate()`，维护成本高、易踩坑 | **建议删除**，统一用 `@RequestBody @Valid` |
| `WebConfig` 拦截器注册 `addPathPatterns("/**")` | 会命中静态资源与 `/error`，且未排除 `/api/auth/**`、`/ws` | 精确注册并配置 `excludePathPatterns` |
| `Result.error(500,"服务器异常")` 兜底 + `e.printStackTrace()` | 打印到 stdout、丢失链路 ID | 改为 slf4j 日志 + `requestId` |
| `application.yaml` | 硬编码 `root/123456`、缺 datasource url、缺 Redis、缺 JWT 配置 | 拆分为 `application.yml` + `application-{dev,prod}.yml`，敏感项全部走环境变量 |
| `local.properties`（含本机 SDK 路径） | **已提交进版本库** | 删除并加入 `.gitignore` |
| `build.gradle` 声明 `org.springframework.boot 4.1.0` + GraalVM 原生插件 + `tools.jackson` | 依赖可用性风险高，且本机无 GraalVM 时会拖慢构建 | 确认仓库中该版本可解析；否则降级到 3.3.x 主线，并把 `tools.jackson.databind.*` 换回 `com.fasterxml.jackson.databind.*` |
| Android 模板页面 | `FirstFragment`/`SecondFragment`/`lorem_ipsum` | 全部替换为登录/会话/联系人/聊天页 |

## 1. 目标架构总览

```
                   ┌──────────────────────────────────────────────┐
   客户端层         │  web-frontend (Vue3+Vite)   android-app (Java) │
                   │     复用同一套 REST + WebSocket 契约            │
                   └───────────────┬──────────────────────────────┘
                        REST /api/v1/**  ·  WS /ws
                                   │
                   ┌───────────────▼──────────────────────────────┐
   后端层           │  backend (Spring Boot, 无状态, 可水平扩容)      │
                   │  auth · user · friend · conversation · message │
                   │  realtime(WS 注册中心 + 分发器)                 │
                   └───────┬───────────────────────┬──────────────┘
                           │                       │
                   ┌───────▼────────┐     ┌────────▼─────────────┐
   数据层           │ MySQL 8 (持久化) │     │ Redis 7 (在线/seq/幂等)│
                   │ database/init   │     │ 限流/token 黑名单      │
                   └────────────────┘     └──────────────────────┘
                   docker-compose 一键启动（数据库层独立成模块）
```

**分层原则**

1. **后端不感知客户端类型**：仅通过 `X-Client-Type: web|android` 做统计与差异化配置，接口契约完全一致。
2. **后端无状态**：不依赖本地 Session；会话态在 JWT、在线态在 Redis、消息态在 MySQL。可多实例部署，WS 跨节点投递走 Redis Pub/Sub。
3. **数据库只被后端访问**：前端与 App 永远不直连 DB；`database/` 模块只提供 docker-compose 与初始化脚本。
4. **统一契约**：所有响应统一 `{code, message, data, requestId, timestamp}`，所有错误统一错误码，Web/App 用同一份错误码表。

## 3. 数据库设计

> 完整 DDL 见 **`database/init/01-schema.sql`**（已落地，可直接被 docker-compose 执行），演示数据见 `02-seed.sql`。

### 3.1 表清单

| # | 表 | 作用 | 关键字段 / 索引 |
|---|---|---|---|
| 1 | `user_account` | 登录凭证 | `user_no` UK、`account` UK、`phone/email` UK、`token_version`、`status` |
| 2 | `user_profile` | 用户资料 | `user_id` UK、`nickname` IDX |
| 3 | `user_device_session` | 多端会话 + refresh 轮换 | `uk(user_id,device_id)`、`refresh_token_hash`、`access_jti`、`refresh_expires_at` |
| 4 | `friend` | 好友关系（双向两行） | `uk(user_id,friend_id)`、`idx(friend_id)` |
| 5 | `friend_request` | 好友申请 | `uk(request_no)`、`idx(to_user_id,status,id)` |
| 6 | `conversation` | 会话（单聊/群聊） | `uk(conversation_no)`、`idx(last_message_at)`、`last_message_seq` |
| 7 | `conversation_member` | 成员 + **未读/已读位点/离线补拉位点** | `uk(conversation_id,user_id)`、`join_seq`、`last_ack_seq`、`last_read_seq`、`unread_count` |
| 8 | `message` | **消息主表** | `uk(msg_no)`、`uk(conversation_id,seq)`、`uk(conversation_id,client_msg_id)`（幂等）、`idx(conversation_id,seq)` |
| 9 | `message_receipt` | 送达/已读回执（可选） | `uk(msg_id,user_id)` |
| 10 | `idempotency_record` | 通用幂等表 | `uk(biz_type,biz_key)`、`idx(expire_at)` |
| 11 | `seq_allocator` | Redis 挂了时的 seq 降级 | `uk(biz_key)` |
| 12 | `chat_group` | 群（二期） | `uk(group_no)` |

### 3.2 关键设计决策

1. **账户 / 资料分离**：`user_account` 只服务鉴权（高频、可缓存到 Redis），`user_profile` 服务展示；避免鉴权查询拖上大字段。
2. **`token_version`**：改密码 / 一键下线所有设备时 `+1`，拦截器比对 Redis 中 `token_version:{uid}`，旧 JWT 立即全部失效（弥补 JWT 无法主动失效的短板）。
3. **会话内单调递增 `seq`**：
   - 历史消息分页：`WHERE conversation_id=? AND seq < ? ORDER BY seq DESC LIMIT n`（走 `idx(conversation_id,seq)`，游标分页，深度翻页无性能衰减）。
   - 离线消息：`WHERE conversation_id=? AND seq > last_ack_seq ORDER BY seq ASC`。
   - 未读数：`seq > last_read_seq` 的条数；由 `unread_count` 冗余字段加速列表展示。
4. **离线消息不单独建表**：用 `conversation_member.last_ack_seq` + `message.seq` 计算，避免"离线表与消息表双写不一致"。量级大时可加 Redis List 做 `offline:{uid}` 队列，仅作为索引加速，MySQL 仍为唯一真相源。
5. **`client_msg_id` 唯一索引做幂等兜底**：不靠应用层 `select then insert`（有并发窗口），而是 DB 唯一约束 + `ON DUPLICATE KEY` / 捕获 `DuplicateKeyException` 回放。
6. **逻辑删除**：`deleted_at` / `status`，消息撤回为 `status=2` 而非物理删除（保留审计）。
7. **字符集** `utf8mb4_0900_ai_ci`，支持 emoji；时间统一 `DATETIME(3)`，由服务端生成，避免多端时钟漂移导致乱序。

## 4. 统一响应格式与错误码

### 4.1 响应体

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "requestId": "7f3c9a21b8e04d5e",
  "timestamp": 1759123456789
}
```

- `code = 0` 表示成功；非 0 为错误码，`data` 固定为 `null`。
- `requestId` 由后端生成并写入 MDC，前端/App 报错时直接回传，便于串联日志。
- 分页统一：`{ "list": [], "hasMore": true, "nextCursor": "12345" }`。

### 4.2 HTTP 状态码映射（与 body.code 同步）

| HTTP | 场景 | body.code |
|---|---|---|
| 200 | 成功 | 0 |
| 400 | 参数校验失败 | 10001 |
| 401 | 未登录 / token 失效 | 10002 / 10003 |
| 403 | 无权限（非好友、非群成员） | 10004 |
| 404 | 资源不存在 | 10005 |
| 429 | 触发限流 | 10006 |
| 500 | 服务异常 | 10007 |

> 约定：**客户端先按 HTTP 状态分流（401→刷新/登出），再按 `body.code` 做细分提示**。Web 用 axios 响应拦截器统一处理，Android 用 OkHttp `Interceptor` 统一处理。

### 4.3 错误码表

| code | 含义 | 客户端动作 |
|---|---|---|
| 0 | success | — |
| 10001 | 参数错误 | 提示 |
| 10002 | 未登录 | 清 token → 跳登录 |
| 10003 | access token 已过期 | 静默 refresh → 重放请求；失败则登出 |
| 10004 | 无权限 | 提示 |
| 10005 | 资源不存在 | 提示 |
| 10006 | 操作过于频繁 | 提示 + 退避 |
| 10007 | 服务异常 | 提示 + 上报 requestId |
| 20001 | 账号已存在 | 提示 |
| 20002 | 账号或密码错误 | 提示（不区分账号是否存在） |
| 20003 | 账号已被禁用/锁定 | 提示 |
| 20004 | refresh token 失效/已轮换 | 强制登出 |
| 20005 | 设备已被踢下线 | 关闭 WS → 登出 |
| 30001 | 不能添加自己 | 提示 |
| 30002 | 已是好友 / 重复申请 | 提示 |
| 30003 | 好友申请不存在或已处理 | 刷新列表 |
| 30004 | 非好友关系 | 提示 |
| 40001 | 会话不存在 | 刷新会话列表 |
| 40002 | 消息内容为空 | 提示 |
| 40003 | 消息体超限 | 提示 |
| 40004 | 重复消息（命中幂等） | 视为成功，用返回的 msgId 更新本地 |

## 5. 用户认证设计

### 5.1 凭证模型

| 凭证 | 形态 | 有效期 | 存储位置 |
|---|---|---|---|
| `accessToken` | JWT (HS256)，载荷 `{uid, userNo, deviceId, tv, typ=access, jti, iat, exp}` | 2 小时 | 内存 + localStorage / EncryptedSharedPreferences |
| `refreshToken` | 32 字节随机串（base64url），**服务端只存 sha256 哈希** | 30 天 | 同上（更安全存储） |

请求头：

```
Authorization: Bearer <accessToken>
X-Device-Id:   <设备唯一ID>
X-Client-Type: web | android
```

### 5.2 登录流程

```
POST /api/v1/auth/login
1. 校验参数（@Valid）→ 失败 10001
2. Redis 查登录失败次数 lock:login:{account}，>=5 次直接 20003
3. 查 user_account（按 account/phone/email），BCrypt.matches 校验
   - 失败 → INCR 失败计数（TTL 5min）→ 20002
   - 成功 → 清零计数
4. status != 1 → 20003
5. UPSERT user_device_session(user_id, device_id)：
   生成 refreshToken（旧 session 立即失效）→ 存 sha256 哈希
6. 签发 accessToken（tv 取 user_account.token_version）
7. 更新 last_login_at/last_login_ip
8. 返回 { accessToken, refreshToken, expiresIn, refreshExpiresIn, user }
```

### 5.3 刷新与轮换

```
POST /api/v1/auth/refresh { refreshToken, deviceId }
1. hash(refreshToken) 查 user_device_session，未命中或 status=0 → 20004（强制登出）
2. 过期 → 20004
3. 轮换：生成新 refreshToken 覆盖 hash，旧 accessJti 加入 Redis 黑名单
   （blacklist:jti:{jti}，TTL = 原 access 剩余有效期）
4. 若发现「已失效的旧 refresh 再次被使用」→ 判定为泄露，吊销该用户该设备全部会话 + token_version+1
5. 返回新的 token 对
```

> 客户端策略：axios/OkHttp 拦截器在收到 **401 + code 10003** 时，**串行**（并发请求共享同一个 refresh Promise/锁）刷新一次，成功后重放原请求；刷新失败则清空本地凭证并跳登录。

### 5.4 登出

```
POST /api/v1/auth/logout（需鉴权）
1. user_device_session.status = 0
2. Redis 拉黑当前 accessJti（TTL=剩余有效期）
3. Redis 删除 ws:online:{uid} 中该 deviceId 的在线记录
4. 向该设备 WS 发送 {"type":"kick"} 后 close；其他端不受影响
5. 客户端清本地 token、断 WS、跳登录
```

### 5.5 身份校验落点

1. **业务接口**：`AuthenticationInterceptor` 注册路径 `/api/v1/**`，排除 `/api/v1/auth/register|login|refresh`、`/actuator/**`、`/static/**`。
   - 解析并验签 JWT → 校验 `exp` → 比对 `tv` 与 Redis `token_version:{uid}` → 检查 `jti` 是否在黑名单 → 查 `user_device_session.status`。
   - 通过则写入 `AuthContext`（ThreadLocal，`finally` 中 `remove()`），控制器用 `@CurrentUser UserContext user` 注入。
   - 方法级可用 `@LoginRequired` 做二次声明（保留现有注解语义，拦截器判断「全局需登录 + 白名单」模式）。
2. **WebSocket 握手**：`AuthHandshakeInterceptor.beforeHandshake` 中校验（见 §7.2）。
3. **群/会话级权限**：Service 层校验 `conversation_member` 中是否存在该 uid，无权限抛 `BizException(10004)`。

### 5.6 安全要点

- 密码 `BCrypt(cost=10)`；`password_algo` 字段预留升级到 Argon2 的平滑迁移。
- JWT 密钥从环境变量 `JWT_SECRET` 注入，禁止入库/入代码；生产用 RS256 非对称。
- 登录/注册/发送接口加 Redis 令牌桶限流（IP + uid 双维度）。
- 全站 HTTPS / WSS；App 端 Android 9+ 默认禁止明文流量，需配 `network_security_config` 允许本地调试域名。
- 消息内容输出前做 XSS 转义（Vue 用 `v-text`，Android 用 `Html.fromHtml` 白名单或纯文本）。

## 7. WebSocket 实时通道

### 7.1 选型说明

采用 **原生 WebSocket + 自定义 JSON 信封**，不使用 STOMP：Android 端只需 OkHttp WebSocket（无需额外 stomp 协议库），Web 端用浏览器原生 `WebSocket`，协议简单、体积小、心跳可控。

### 7.2 握手与鉴权

```
WS 地址：ws://{host}/ws?token={accessToken}&deviceId={deviceId}
        （兼容用法：Sec-WebSocket-Protocol: access_token.{token}）
```

`AuthHandshakeInterceptor.beforeHandshake`：
1. 从 query / 子协议头取 token（浏览器原生 WS 不能自定义 header，故用 query 或子协议）；
2. 复用与 HTTP 完全相同的 JWT 校验逻辑（签名、过期、`tv`、黑名单、设备状态）；
3. 校验通过 → `attributes.put("uid", uid)`、`attributes.put("deviceId", deviceId)`；
4. 校验失败 → `response.setStatusCode(HttpStatus.UNAUTHORIZED)` 并 `return false`，**拒绝升级**；客户端收到 401 后应先 refresh 再重连。

> 安全补充：token 出现在 URL 中会被访问日志记录，生产环境建议改为「先用 REST 换一个 60 秒有效的一次性 `wsTicket`，再用 ticket 握手」，`/auth/ws-ticket` 接口预留。

### 7.3 协议信封

```json
{
  "type": "chat | ack | read | typing | notify | ping | pong | kick | error",
  "seq":  12345,
  "ts":   1759123456789,
  "data": { }
}
```

**上行（客户端 → 服务端）**

| type | data | 说明 |
|---|---|---|
| `chat` | `{clientMsgId, conversationId, msgType, content, extra}` | 发送消息（与 `POST /messages` 走同一 Service） |
| `read` | `{conversationId, lastReadSeq}` | 已读上报 |
| `typing` | `{conversationId}` | 正在输入 |
| `ping` | `{}` | 心跳 |

**下行（服务端 → 客户端）**

| type | data | 说明 |
|---|---|---|
| `connected` | `{userId, deviceId, serverTime}` | 握手成功 |
| `chat` | `MessageVO` | 新消息（含自己其他端发的） |
| `ack` | `{clientMsgId, msgNo, seq, sendTime}` | 上行消息落库确认 |
| `read` | `{conversationId, lastReadSeq, userId}` | 对方/其他端已读 |
| `typing` | `{conversationId, userId}` | — |
| `notify` | `{kind:"friend_request"\|"friend_accepted"\|"recall", payload}` | 系统通知 |
| `pong` | `{ts}` | 心跳应答 |
| `kick` | `{reason:"logout"\|"other_login"\|"password_changed"}` | 强制下线，随后服务端 close |
| `error` | `{code, message}` | 协议级错误 |

### 7.4 心跳保活

| 项 | 策略 |
|---|---|
| 客户端心跳 | 每 **30s** 发 `ping`；连续 2 次（60s）未收到 `pong` → 判定断线，主动关闭并重连 |
| 服务端心跳 | 每 **25s** 下发 `ping`（兜底探测半开连接） |
| 服务端超时 | **90s** 未收到任何帧 → `session.close(CloseStatus(4000,"heartbeat timeout"))`，清理本地与 Redis 在线记录 |
| Android 保活 | 前台服务 + `NetworkCallback` 监听网络恢复立即重连；App 退后台时 WS 断开，靠厂商推送/下次进前台 sync 补齐 |
| Web 保活 | 监听 `visibilitychange`/`online` 事件；页面隐藏时不主动断线（可视服务端压力调整） |

### 7.5 断线重连

```
退避序列：1s → 2s → 4s → 8s → 16s → 30s（上限），每档叠加 0~1000ms 随机抖动（防惊群）
触发时机：onClose / onFailure / 心跳超时 / 网络恢复 / 前台回到前台
重连流程：
  1. 若 accessToken 已过期（或上次关闭码为 401）→ 先调 /auth/refresh，失败则跳登录
  2. 重新握手 /ws?token=...
  3. 收到 connected 后 POST /messages/sync {items:[{conversationId, lastAckSeq}]} 补齐离线消息
  4. flush 本地待发队列（按 clientMsgId 重发，服务端幂等）
```

### 7.6 多端在线状态管理

- Redis：`HSET ws:online:{userId} {deviceId} {json:{nodeId, sessionId, platform, loginAt}}`，字段 TTL 45s，**每次心跳续期**（避免进程异常退出留下僵尸在线）。
- 本地：`ConcurrentHashMap<Long userId, Map<String deviceId, WebSocketSession>>`（单节点内 O(1) 定位）。
- 跨节点：后端多实例时，投递消息前查 Redis 在线表；目标 session 不在本节点 → 通过 Redis Pub/Sub `ws:dispatch` 广播 `{userId, payload, excludeDeviceId}`，由持有该 session 的节点执行实际发送。
- 状态变更事件：用户上线/下线时向其好友推送 `notify`（`kind:"presence"`），会话列表展示在线小绿点。
- 推送范围：接收方的**全部在线设备**；发送方的**其他设备**（排除 `excludeDeviceId`，避免本端重复渲染）。

## 8. 消息时序

### 8.1 场景 A：双方在线，实时收发

```
A 客户端                A 节点后端               MySQL/Redis            B 节点后端         B 客户端
  │ 1 POST /messages ─────▶│
  │  (clientMsgId=uuid)    │ 2 鉴权 + 校验会话成员
  │                        │ 3 Redis INCR seq:conv:1 → seq=12
  │                        │ 4 INSERT message ─────────▶│  (uk_conv_client_msg 幂等兜底)
  │                        │ 5 UPDATE conversation
  │                        │   SET last_message_seq=12 WHERE id=1 AND last_message_seq<12
  │                        │ 6 UPDATE conversation_member SET unread=unread+1 (B)
  │                        │ 7 查 ws:online:{B} → 定位节点/device
  │ 8 ◀── 200 MessageVO ───│                                  │ 9 push chat ────────▶│
  │   (本地按 clientMsgId                                      │   (B 所有在线端)      │ 10 落本地库
  │    把"发送中"置为成功)                                     │                      │ 11 上行 read/ack
  │                        │                                  │◀─────────────────────│
  │ 12 ◀── WS chat(A的其他设备，排除本端)                                              │
```

**要点**：HTTP 响应先返回（客户端立即拿到 `seq`/`msgNo`），WS 推送异步进行；**HTTP 用于可靠性（可重试、幂等、离线兜底），WS 用于实时性**。WS 上行 `chat` 走同一 `MessageService`，适用于弱网下减少一次 RTT，但客户端必须支持失败后降级到 HTTP 重发。

### 8.2 场景 B：接收方离线

```
1~6 同上（消息照常落库，unread_count+1，last_ack_seq 不动）
7 查 ws:online:{B} 为空 → 不推送，直接返回成功
8 B 上线 → 握手 → POST /messages/sync {items:[{convId:1, afterSeq:9}]}
9 服务端 SELECT * FROM message WHERE conversation_id=1 AND seq>9 ORDER BY seq ASC LIMIT 200
10 B 本地按 msg_no 唯一索引去重后入库，更新 last_ack_seq=12，会话列表未读数=12-9=3
11 B 点开会话 → POST /conversations/1/read {lastReadSeq:12} → unread_count 归零
   → 服务端向 A 推送 {type:"read", data:{conversationId:1,lastReadSeq:12}}
```

### 8.3 场景 C：历史消息分页

```
首次进入会话：GET /conversations/1/messages?size=20            （不带 cursor，取最新 20 条，倒序后正序展示）
向上滚动：   GET /conversations/1/messages?cursor=<当前列表最小 seq>&size=20&direction=backward
SQL：SELECT ... WHERE conversation_id=? AND seq < ? ORDER BY seq DESC LIMIT 21
     （多查 1 条判断 hasMore；走 idx(conversation_id,seq)，深度翻页性能恒定）
```

### 8.4 场景 D：弱网 / 断网重连补洞

```
网络恢复 → 指数退避重连 → connected → /messages/sync 补 seq>lastAckSeq 的消息
→ 本地库按 (conversation_id, seq) 排序渲染；若发现 seq 空洞（缺失 N+1）→ 再拉一次 /messages?cursor
→ 待发队列 flush：逐条 POST /messages（复用原 clientMsgId，命中幂等直接返回原 msgNo，不产生重复消息）
```

## 9. 并发与幂等处理策略

### 9.1 消息发送幂等

| 层 | 手段 |
|---|---|
| 客户端 | 生成 `clientMsgId = UUID v4`，**任何重试都复用同一个 ID**（本地库唯一索引 `(conversation_id, client_msg_id)`） |
| 传输 | 优先 `POST /messages`（HTTP 语义清晰、可重试）；WS 上行失败自动降级 HTTP |
| 服务端 | `INSERT` 命中 `uk_conv_client_msg` → 捕获 `DuplicateKeyException` → 查询已有消息 → 返回 `duplicated=true` 的同一 `MessageVO`（**幂等回放**，不产生第二条消息） |
| 兜底 | `idempotency_record` 表（`biz_type=send_msg`，`biz_key=uid:clientMsgId`）保存首次结果，7 天过期，定时清理 |

### 9.2 序号（seq）并发分配

- 正常路径：`Redis INCR seq:conv:{conversationId}`（原子、高性能）；数据库 `uk(conversation_id, seq)` 作为最终一致性兜底，冲突时重新取号重试（最多 3 次）。
- 降级路径：Redis 不可用时走 `seq_allocator` 表（乐观锁 `version` + 号段预取 100 个/次，避免每条消息一次 DB 写）。
- **禁止**使用 `SELECT MAX(seq)+1`（并发下必然冲突），也**不要**用客户端时间戳排序（多端时钟漂移）。

### 9.3 会话摘要并发覆盖

```sql
UPDATE conversation
   SET last_message_id = ?, last_message_seq = ?, last_message_preview = ?, last_message_at = ?
 WHERE id = ? AND last_message_seq < ?;   -- 旧消息到达时不会覆盖新摘要
```

### 9.4 未读数

- 自增：`UPDATE conversation_member SET unread_count = unread_count + 1 WHERE conversation_id=? AND user_id=?`（行锁，原子）。
- 已读：`UPDATE ... SET last_read_seq = GREATEST(last_read_seq, ?), unread_count = 0 WHERE ...`（防止旧消息/乱序请求把位点回退）。
- 未读数以 `seq - last_read_seq` 为准做对账修复，避免长期运行后与真实值漂移（每日低峰 job 校准）。

### 9.5 创建单聊会话的并发

1. 计算确定性键：`convKey = "P" + min(uidA,uidB) + "_" + max(uidA,uidB)`，以此生成 `conversation_no`。
2. 分布式锁 `lock:conv:{convKey}`（Redis SETNX，TTL 5s）。
3. 数据库 `uk(conversation_no)` 唯一索引兜底；冲突则回查已有会话返回。
4. 结果：并发的双方同时发起会话创建，**只会产生一个会话**。

### 9.6 好友操作

- 加好友：`uk(user_id, friend_id)` + 幂等记录；同意操作用 `friend_request.status` CAS（`UPDATE ... SET status=1 WHERE id=? AND status=0`，影响行数 0 → 抛 30003）。
- 申请去重：`idx(from_user_id, to_user_id)` 查询 + 未处理申请存在则返回 30002。

### 9.7 WebSocket 并发写

- `WebSocketSession` 非线程安全：用 Spring 提供的 `ConcurrentWebSocketSessionDecorator` 包装（发送缓冲区 8KB、发送超时 5s），避免多线程同时 `sendMessage` 抛异常。
- 注册表用 `ConcurrentHashMap`；单 session 关闭时先移除再 close，避免 close 期间被读到。
- 推送失败（buffer overflow / 发送超时）→ 立即关闭该 session，触发客户端重连，防止静默丢消息。

### 9.8 刷新令牌并发

- 多请求同时 401 时，客户端**只允许一个 refresh 在飞**（Web：共享 Promise；Android：`synchronized` + 标记位），其余请求挂起等待后重放，避免 refresh 轮换把前面的 token 作废导致连锁失败。
- 服务端对同一 `deviceId` 的 refresh 串行化（Redis 锁），检测到旧 refresh 复用则判定泄露并整体吊销。

### 9.9 其他

- 限流：Redis 令牌桶，`{uid}:{api}` 维度（发消息 60 次/分钟、加好友 20 次/天、登录 10 次/分钟），超限返回 10006。
- 文件上传：`md5` 秒传 + `biz_key=uid:md5` 幂等；大小/类型白名单校验。
- 接口响应统一带 `requestId`，所有异常打日志但不回传堆栈。

## 10. Web 前端实现要点（Vue 3 + Vite）

1. **`api/http.js`**：axios 实例，`baseURL: '/api'`，请求拦截注入 `Authorization` / `X-Device-Id` / `X-Client-Type`；响应拦截：`code===0` 解包返回 `data`，`code===10003` 触发 refresh 后重放（并发共享 Promise），其余抛 `AppError{code,message,requestId}`。
2. **`ws/socket.js`**：`WebSocketManager` 单例
   - `connect(token)` / `close()` / `send(envelope)`；
   - 心跳定时器 30s ping，60s 无 pong 判死；
   - 指数退避重连（1→30s + 抖动），重连前先 `ensureToken()`；
   - 断线期间 `sendQueue` 缓存，恢复后 flush；
   - 事件用 `mitt` 或 Pinia action 分发到 `message/conversation` store。
3. **状态管理（Pinia）**：`user`（token、profile）、`conversation`（列表、未读总数）、`message`（按 `conversationId` 分片的消息 Map + `lastAckSeq`）。
4. **消息渲染**：`key` 用 `msgNo`；按 `seq` 排序；本地"发送中/失败"态由 `clientMsgId` 关联，`ack` 到达后替换为服务端数据。
5. **登录成功后立即建连**：`Login` 成功 → 保存 token → `ws.connect()` → 拉取会话列表 → 路由进 Home。
6. **Vite 代理**：`/api` → `http://localhost:3001`，`/ws` → `ws://localhost:3001`（`ws: true`），避免开发期跨域。

## 11. Android 端实现要点（Java + XML）

1. **依赖新增**（`libs.versions.toml`）：`okhttp 4.12.0`、`gson 2.11.0`、`androidx.recyclerview`、`androidx.lifecycle:lifecycle-livedata/viewmodel`、`androidx.security:security-crypto 1.1.0`（`EncryptedSharedPreferences` 存 token）、可选 `androidx.room`（本地消息缓存）。**保持 Java + XML，不引入 Kotlin / Compose**。
2. **`ApiService`**：单例 `OkHttpClient`，`AuthInterceptor` 自动加头；`Authenticator` 或自定义拦截器处理 401 → refresh → 重放（加 `synchronized` 保证单飞）。
3. **`WsManager`**：基于 OkHttp `WebSocket`
   - `connect()`/`disconnect()`/`send()`；`ScheduledExecutorService` 30s ping；
   - `onFailure/onClosing` → 退避重连；`NetworkCallback` 监听网络可用立即重连；
   - 用 `LiveData` / 本地广播把 `chat/notify/read/kick` 事件分发到 UI；
   - `kick` 事件 → 清 token → 跳 `LoginActivity`（`FLAG_ACTIVITY_CLEAR_TASK`）。
4. **本地缓存**：SQLite（Room）建 `message` 表，`msg_no` 唯一、`(conversation_id, seq)` 索引；离线打开会话先读本地，再 `/messages/sync` 增量更新。
5. **页面与布局（XML）**：`activity_login.xml`（账号/密码/登录/注册）、`activity_main.xml`（`BottomNavigationView` + `NavHostFragment`：会话 / 联系人 / 我的）、`activity_chat.xml`（`RecyclerView` + 输入栏）、`item_message_left.xml` / `item_message_right.xml`、`item_conversation.xml`。
6. **权限与配置**：`INTERNET`、`ACCESS_NETWORK_STATE`；`networkSecurityConfig` 放开本地 http 调试；`android:usesCleartextTraffic` 仅 debug 变体开启。
7. **生命周期**：`MainActivity.onStart()` 建连、`onStop()` 不主动断（后台靠心跳），`onDestroy()` 释放；进程被杀后冷启动走 `/auth/me` 校验 → 刷新 → 建连 → sync。

### A. 拦截器核心（替换 `LoginInterceptor`）

```java
@Override
public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
    if (!(handler instanceof HandlerMethod hm)) return true;
    if (hm.hasMethodAnnotation(PublicApi.class)) return true;      // 白名单注解替代手写路径
    String token = resolveToken(req);                              // Bearer → JWT
    if (token == null) throw new BizException(ResultCode.UNAUTHORIZED);
    JwtClaims c = jwtTokenProvider.parse(token);
    if (!"access".equals(c.getTyp()))            throw new BizException(ResultCode.UNAUTHORIZED);
    if (tokenBlacklistService.isBlacklisted(c.getJti())) throw new BizException(ResultCode.TOKEN_EXPIRED);
    if (c.getTv() != tokenVersionService.get(c.getUid())) throw new BizException(ResultCode.KICKED);
    AuthContext.set(new UserContext(c.getUid(), c.getUserNo(), c.getDeviceId()));
    return true;                                                   // afterCompletion 中 AuthContext.clear()
}
```

### B. WS 握手鉴权

```java
public boolean beforeHandshake(ServerHttpRequest req, ServerHttpResponse resp,
                               WebSocketHandler h, Map<String,Object> attrs) {
    String token = resolveTokenFromQueryOrProtocol(req);
    try {
        JwtClaims c = jwtTokenProvider.parse(token);
        checkTokenVersionAndBlacklist(c);
        attrs.put(AuthConst.UID, c.getUid());
        attrs.put(AuthConst.DEVICE_ID, c.getDeviceId());
        return true;
    } catch (BizException e) {
        resp.setStatusCode(HttpStatus.UNAUTHORIZED);
        return false;                       // 客户端收到 401 → refresh 后重连
    }
}

### C. 消息发送事务边界

```
1) Redis INCR seq                       （非事务，允许极小概率空洞）

### D. 客户端重连伪码（Web / Android 通用）

```
onClose/onFailure:
  if (closingCode == 401 || tokenExpiringSoon()) await refreshToken()
  delay = min(30s, 1s * 2^failCount) + random(0,1000ms)
  scheduleReconnect(delay); failCount++
onConnected:
  failCount = 0; startHeartbeat(30s)
  sync(lastAckSeqMap) → flushSendQueue()
onPongTimeout(60s): forceClose() → 走 onClose 分支
```
