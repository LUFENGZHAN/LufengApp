## 排障：登录返回 code=10007 服务异常（已修复，全链路跑通）

用户反馈前端登录报 10007。排查顺序与根因（三个问题叠在一起）：
1. 后端 GlobalExceptionHandler 把 Exception 统一吞成 "服务异常"，看不到根因。
   → 改进：dev/local/default profile 下把 root cause 拼进 message（用 Environment 读 spring.profiles.active，生产仍隐藏）。
2. 宿主机 3306 被**其他项目容器 chat-mysql** 占用 → 我们的 lufeng-mysql 停在 Created / 拿到容器但没有 host 端口映射
   （docker ps Ports 列只显示 3306/tcp 而非 0.0.0.0:3307->3306/tcp）→ 后端连到别人的库，表不存在 → 10007。
   → 修复：compose mysql ports 改为 `${MYSQL_HOST_PORT:-3307}:3306`；application.yml 默认 url 端口改 3307（保留环境变量覆盖）。
   → 判断技巧：health 200（不查库）但业务接口全挂，且 Hikari 能建连却报 SQL 错，多半是连错实例。
3. **真正致命的 bug**：JDBC URL 里 `characterEncoding=utf8mb4` 非法（这是 MySQL 字符集名，不是 JDBC 参数值），
   抛 Unsupported character encoding 'utf8mb4' → 所有查库接口 10007。
   → 改 `characterEncoding=UTF-8`。已全局修：backend/application.yml、database/README、docker-compose 注释、docs 方案文档。
4. 顺带发现中文双重编码：docker-entrypoint 对**每个** .sql 文件独立会话执行，01-schema.sql 的 SET NAMES 不影响 02-seed.sql，
   seed 以 latin1 会话插入 → nickname 存成 C3A5C2BC...（正确应为 E5BCA0）。
   → 02-seed.sql 开头加 SET NAMES utf8mb4；compose 加 --character-set-client-handshake=FALSE 兜底；down -v 重建后 HEX 校验通过。
   → 判别方法：select hex(col) 比对真实字节，别信终端回显（终端会话 latin1 会把正确数据也显示成乱码）。

其它记录：
- 3001 上的后端 java 进程（PID 34628）用户自行启动，taskkill 拒绝访问，无法代重启；用 3002 另起实例验证后kill掉。
- 新增 database/scripts/ws-smoke.mjs（Node 22 内置 fetch+WebSocket，零依赖全链路冒烟脚本，已验证通过）。

## 排障：申请好友报 SQLIntegrityConstraintViolationException: Column 'apply_msg' cannot be null

根因：`friend_request.apply_msg` 声明为 `NOT NULL DEFAULT ''`，但 MyBatis 的 INSERT **显式写入了 `#{applyMsg}` = null**。
**MySQL 的列级 DEFAULT 只在不写该列时生效，显式插入 NULL 仍报 1048** —— 这是最容易误判的点（看到 DEFAULT '' 就以为安全）。
调用链：前端 AddFriendDialog 的 `apply()` 只传 `{ toUserId }`，从来没传过 applyMsg → 后端照搬 null → 1048。

修复（三层防御）：
1. Service 语义兜底：`FriendServiceImpl.normalizeApplyMsg()` —— null/空白 → 默认文案「请求添加你为好友」，trim，超 255 截断。
2. Mapper SQL 兜底：`ifnull(#{applyMsg}, '')`、`ifnull(#{remark}, '')`、`ifnull(#{source}, 'search')`。
3. 前端补输入：`AddFriendDialog` 加「验证消息（可选）」输入框，`applyMsg: msg || undefined`。

顺带排查出**同类隐患两处**（都是显式插 NULL 到 NOT NULL 列，不修迟早复现）：
- `AuthServiceImpl.register` 建 `UserProfile` 时没设 avatar/signature → avatar 是 NOT NULL → **注册接口本身也是坏的**。
  → 新增 `common/constant/Defaults.AVATAR`，注册与 `UserServiceImpl` 补建资料时都用它。
- `UserProfileMapper.updateSelective` 全字段为 null 时会拼出 `update user_profile where user_id=?` 的非法 SQL
  → `UserServiceImpl.update` 加全空跳过判断。
- `friend.remark` 同为 NOT NULL：`remark()` 原先用 `insertIgnoreDuplicate` 更新（空值不覆盖，导致"清空备注"失效）
  → 新增 `FriendMapper.updateRemark` 精确更新；`insertIgnoreDuplicate` 改语义为「空值不覆盖旧备注」。

新增 `database/scripts/friend-smoke.mjs`（好友链路冒烟：登录→申请(不传留言)→重复拦截→接收方看默认文案→同意→
双向好友+自动建会话→备注设置与清空）。冒烟 9 步全通；注册接口也验证通过（avatar 默认头像已落库）。

**方法论：遇到 1048 不要只改一个字段，要把所有 INSERT 语句与 NOT NULL 列交叉核对一遍**（`grep -A6 "@Insert"` + 看 DDL）。

## 重构：删除好友的完整语义（解除关系 + 解散会话 + 可恢复）

用户反馈「同意好友申请报 remark cannot be null」+「删除好友后收发消息异常」。

1. **accept 报 remark null**：与 apply_msg 同源（FriendMapper 已加 ifnull），但用户跑的是旧进程；
   为彻底杜绝，给 `Friend` 实体字段加默认值 `private String remark = "";` + `addRelation` 显式 setRemark("")。
   实体层默认值比 SQL 兜底更早生效，是这三道防线里最靠前的一道。

2. **删除好友语义缺失（真正的业务逻辑 bug）**：原来 `delete()` 只做 `friendMapper.deleteBoth`，
   会话成员完全没动 → 关系没了但会话还在，双方仍能收发消息（前端虽然本地 remove 了会话，服务端照样推）。
   新语义（FriendServiceImpl.delete）：
   - `friendMapper.deleteBoth` 双向解除
   - `conversationService.dissolvePrivate(userId, friendId)` 双方 `is_deleted=1`、未读清零
     → 会话从双方列表消失；`requireMember` 抛错 → 不能发；`listMemberIds` 过滤 is_deleted=0 → 没人收得到
   - `friendRequestMapper.invalidateHandled` 把双方「已同意」的历史申请置为 3（已忽略），避免列表残留
   - 发布两个 WS notify：`friend_removed`（给对方，带提示）/ `friend_deleted`（给自己其他端，静默只刷会话）

3. **重新加回好友必须能恢复会话**（否则出现「好友列表里有他，但发消息报不是会话成员」的死局）：
   `ConversationServiceImpl.createPrivate` 命中已有会话时走新增的 `reopen()` → 双向 `addMember`
   （insertIgnoreDuplicate 的 on duplicate key 只置 is_deleted=0，ack/read 位点不变 → 历史消息可见）。

4. **历史数据坑**：早期 seed 把会话号写死成 `C00000001`，而 `IdGenerator.conversationNo("P1_2")` 生成 `CP1_2`，
   只按 no 查找会给同一对人建出**第二个会话**。
   → `findExisting()` 先按 no 找，再按成员对兜底（新增 `ConversationMapper.findPrivateBetween`）；
     同时把 seed 的会话号改成 `CP1_2` 保持一致。
   → `dissolvePrivate` 也用 findPrivateBetween，不依赖会话号格式。

5. 发消息的错误文案：`MessageServiceImpl.requireSender` 捕获成员校验异常，单聊时改抛
   NOT_FRIEND「好友关系已解除，无法发送消息」，不再显示莫名其妙的「不是该会话成员」。

6. 存量脏数据修复脚本：`database/scripts/fix-orphan-private-conversations.sql`
   （把「好友关系缺失但成员仍活跃」的单聊双方置为已退出）。已在当前 dev 库执行，影响 2 行。

7. `ws-smoke.mjs` 增加 2.5 步自愈：若 zhangsan↔lisi 不是好友或会话已解散，自动申请+同意+`POST /conversations/private`，
   保证脚本可重复执行（原来直接取 `convs.data[0]`，会话解散后就选错人了）。

校验：friend-smoke 扩到 14 步全通（含「删除→双方会话消失→发消息被拒→重新加回→会话 ID 不变→历史 5 条→可再发」）；
ws-smoke 7 步全通；vue-tsc 0 error；npm run build 通过。

**设计原则：单聊会话的生命周期绑定好友关系——关系解除即解散会话（软退出、历史保留），关系恢复即恢复会话（复用同一会话）。
不要用「会话号」当唯一依据，用「成员对」兜底，历史数据才不会分裂。**

## 会话创建改为懒创建（用户要求：添加好友不用默认创建聊天）

**语义变更**：同意好友申请**不再** `createPrivate`，会话改为「第一条消息发出时才创建」。
- 后端：`FriendServiceImpl.handle` 移除 `conversationService.createPrivate(...)`（仅保留双向写 friend）。
- 后端：`SendMessageReq` 新增 `peerId`；`conversationId` 去掉 `@NotNull`，与 peerId 二选一。
- 后端：`MessageServiceImpl.resolveConversationId()`：只有 peerId 时校验 `friendService.isFriend`
  （非好友抛 NOT_FRIEND/30004）→ `createPrivate` 懒建 → 用返回的会话号继续走原发送逻辑。

## 会话列表增加「删除会话」功能

用户反馈：不能删除会话列表（前端无删除入口）。

排查：后端 `DELETE /api/v1/conversations/{id}`（ConversationServiceImpl.delete → conversationMemberMapper.softDelete 置 is_deleted=1）早已存在，
`listByUser` 也按 `cm.is_deleted=0` 过滤，逻辑正确；缺的是前端触发入口（ConversationList 无删除按钮，store.remove 只本地过滤没调接口）。

改动：
- `web-app/src/stores/conversation.ts`：新增 `deleteConversation(id)` = `conversationApi.remove(id)` + 本地 `remove`（同时清 currentId）。
- `web-app/src/components/chat/ConversationList.vue`：每个会话项 hover 显示红色删除按钮（AppIcon trash），
  `onDelete` 调 `deleteConversation` + `window.confirm` 二次确认；删的是当前会话则 `router.replace({name:'chat'})` 回到占位页。
  样式：`.item-wrap` 包 RouterLink + 绝对定位 `.del`，hover 时 `.item` 右移 44px 给按钮留位，避免遮挡时间/未读。
- 语义：删除=本端软退出，会话从列表消失、不再收该会话消息；消息保留，对方无感；重新给对方发消息（peerId）会经 createPrivate 的
  insertIgnoreDuplicate(is_deleted=0) 复用同一会话恢复。与「删除好友」(dissolvePrivate 双向软删) 相互独立。

验证：`npm run build` 通过（vue-tsc 0 error）；对运行中的 3001 后端 curl 实测：删 cid=2 前列表 1 条、删后 0 条，过滤生效。
注意：此删除动作会改 DB，测试时在 zhangsan 名下删掉了与王五的会话（cid=2），对方视角仍在，属预期。
